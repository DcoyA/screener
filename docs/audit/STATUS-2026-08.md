  - 섹터 미매핑: [scripts/update_data.py:1860](../../scripts/update_data.py#L1860) → `status: "sector_unmapped"`
- `MIN_LOO_SECTOR_SAMPLE = 2` / `MIN_LOO_MARKET_SAMPLE = 10` ([scripts/update_data.py:72-73](../../scripts/update_data.py#L72)) — 주석([scripts/update_data.py:68-71](../../scripts/update_data.py#L68))이 "n=1이면 회귀가 자기 자신으로 수렴해 target==close가 강제되던 문제"를 명시하고 그걸 막기 위해 도입됨
- 상승여력 가중치 재배분: [scripts/update_data.py:1078-1085](../../scripts/update_data.py#L1078) — `has_upside`가 False면 `upside_weight = 0.0`, 그 0.15를 모멘텀 항으로 이전. `totalScore`(= value+quality+safety+market+change − penalty, [scripts/update_data.py:1251-1252](../../scripts/update_data.py#L1251))에는 원래부터 상승여력 항이 없음.
- 표시 계층 방어: [app/lib/formatUpside.js:15-17](../../app/lib/formatUpside.js#L15) `fair === current` → "산출 보류"

**그러나 배포된 데이터는 여전히 현재가 == 적정가**
```
006730 서부티엔디  close 10740  target 10740  tLow 10740  tHigh 10740  upside 0
383220 F&F        close 62800  target 62800  tLow 62800  tHigh 62800  upside 0
041510 에스엠      close 72100  target 72100  tLow 69999  tHigh 74961  upside 0   ← mid만 붕괴
299660 셀리드      close 2395   target null   (status 없음, fairValueMeta.sectorCode=null)
```
(`node`로 `app/data/stocks.json` 직접 조회)

**원인 특정**
- 세 종목 모두 `fairValueMeta.sectorSampleSize: 1`, `sectorSampleTier: "sector_small"`. 이 조합은 **현재 코드에서는 나올 수 없다** — `sector_small` 티어는 `loo_sector_stats["n"] >= MIN_LOO_SECTOR_SAMPLE(2)`일 때만 배정됨([scripts/update_data.py:1874-1877](../../scripts/update_data.py#L1874)). `n=1`이면 시장 폴백 또는 `insufficient_data`로 가야 한다.
- 즉 배포 중인 `app/data/stocks.json`은 **leave-one-out 수정(634f7b7, 8/26 13:11 KST) 이전** 코드로 생성됨. 마지막 `stocks.json` 커밋은 `584e80e "Update weekday JSON data"` (2026-08-26 02:14 UTC = **11:14 KST**) — fix보다 약 2시간 전.
- 그 옛 코드 경로에서 target==close가 나온 메커니즘: 섹터 표본이 사실상 자기 자신뿐(n=1)이라 `target_per_mid = per + λ·(p50 − per)`에서 `p50 ≈ per`가 되고 `λ=0.15`(작음)까지 곱해져 `target_per_mid ≈ per_value` → `int(close_price · target_per_mid/per_value) == close_price` ([scripts/update_data.py:1896](../../scripts/update_data.py#L1896), [1900](../../scripts/update_data.py#L1900)). 에스엠은 `p25/p75`는 달라서 low/high만 움직이고 mid만 붕괴.
- 파이프라인이 8/25 이후 안 돌아(P0-emergency 배경) 재생성이 안 됨 → 수정된 코드가 데이터에 반영되지 못함.

**품질 게이트 공백**
- [scripts/validate_pipeline_output.py:189-206](../../scripts/validate_pipeline_output.py#L189)는 `fair_value_null_ratio`만 검사. `targetPrice == closePrice`(fallback 시그니처)를 잡는 체크가 없어, 재실행돼도 서부티엔디/F&F 같은 케이스는 통과된다.

### 결론
파이프라인 로직에서 명시적 fallback은 제거됐고 사유 enum·가중치 재배분도 구현됨. 그러나 배포 데이터가 수정 이전 산출물이라 서부티엔디(006730)·F&F(383220)가 여전히 현재가==적정가·상승여력 0으로 나온다. 파이프라인 1회 재실행 + target==close 품질게이트 추가가 남음.

### 판정: **[부분완료]** (조회 코드·테이블은 정상, 데이터 축적 기간이 부족)

### 근거

**과거 스냅샷 테이블은 실제로 존재하고 시계열로 쌓인다**
- 테이블: `stock_daily_snapshots`, PK `(code, snapshot_date)`
- 적재기: [scripts/ingest-daily-snapshot.mjs:74-122](../../scripts/ingest-daily-snapshot.mjs#L74) `mapToSnapshotRow` — `snapshot_date`([77](../../scripts/ingest-daily-snapshot.mjs#L77)), `unified_grade_code`([118](../../scripts/ingest-daily-snapshot.mjs#L118)), `raw_data` 통째([120](../../scripts/ingest-daily-snapshot.mjs#L120)) 저장. upsert `onConflict: "code,snapshot_date"` ([130](../../scripts/ingest-daily-snapshot.mjs#L130))
- 실행: `.github/workflows/sync-supabase.yml:23` (stocks.json push 시), `.github/workflows/weekly-json-update.yml:147` (평일 파이프라인 끝)
- `latest_stock_snapshots`는 이 테이블 기반 뷰 (docs/supabase-v2-migration.sql:26-31)

**조회 코드도 정상 (문서 스펙대로)**
- [app/lib/gradeHistory.js:4](../../app/lib/gradeHistory.js#L4) `LOOKBACK_WEEKS = [12, 8, 4]`
- [app/lib/gradeHistory.js:19-31](../../app/lib/gradeHistory.js#L19) `stock_daily_snapshots`에서 `unified_grade_code` 조회, `snapshot_date <= (오늘 − weeks·7일)` 중 가장 최근 1건
- [app/lib/gradeHistory.js:29](../../app/lib/gradeHistory.js#L29) 못 찾으면 `null` 반환 (보간 안 함 — 문서 "보간 금지" 준수)
- 렌더: [app/stock/[code]/page.js:227-270](../../app/stock/[code]/page.js#L227) — `point.grade || "-"`

**"-"가 나오는 근본 원인: 룩백 창이 테이블 나이보다 길다**
- `scripts/ingest-daily-snapshot.mjs` 최초 커밋 **2026-08-16** (`7ff0312`). 오늘 2026-08-27 → 테이블에 최대 약 11일치(평일만 + 8/25 이후 파이프라인 중단이면 더 적음).
- 룩백 목표일: 4주 전 = 2026-07-30, 8주 전 = 2026-07-02, 12주 전 = 2026-06-04 → **셋 다 테이블의 가장 이른 행(2026-08-16)보다 앞** → `fetchGradeAsOf`가 세 시점 모두 `null` → 타임라인의 과거 3칸이 전부 "-", "현재" 칸만 등급 표시.
- 기능 자체가 방금 도입됨: [app/lib/gradeHistory.js](../../app/lib/gradeHistory.js) 최초 커밋 `889ff17` (2026-08-26). 데이터가 12주치 쌓이는 시점(~2026-11-08)까지 과거 칸은 구조적으로 "-".
- 부차적(원인 아님): [app/lib/gradeHistory.js:9-13](../../app/lib/gradeHistory.js#L9) `daysAgoStr`는 UTC(`getUTCDate`) 기준, 적재기는 KST `snapshot_date` — 최대 1일 오차. "전부 -"의 원인은 아님.
- P1-logic-fix TASK 3.1의 전제("`latest_stock_snapshots`에 이미 시계열이 있다. 추가 수집 불필요")는 부정확 — `latest_*`는 코드당 1행 뷰이고, 시계열은 `stock_daily_snapshots`이며 2026-08-16부터만 존재한다.

### 결론
테이블도 있고 적재기·조회 코드도 문서 스펙대로 구현돼 있다. 하지만 스냅샷 축적이 2026-08-16에 시작돼 4/8/12주 룩백이 데이터를 만날 수 없어 과거 3칸이 모두 "-"로 나온다. 코드 버그가 아니라 데이터 성숙도 문제이며, 시간이 지나면(테이블이 각 룩백 깊이를 넘기면) 자동 해소된다.
